# Maintenance and sustainable growth

This project aims to earn attention by being useful, reliable, and welcoming. Stars are a discovery signal, not a reason to compromise quality or send unwanted promotion.

## Seven-day launch plan

| Day | Focus | Useful outcome |
|---|---|---|
| 0 | Initial release | Tested CLI, clear quick start, community files, CI, actionable roadmap |
| 1 | Feedback and correctness | Triage every new issue/PR; fix installation or cross-platform problems |
| 2 | Remote repository checks | Optional GitHub metadata insights without requiring credentials for local audits |
| 3 | Configuration | Let repositories opt into relevant checks and fair thresholds |
| 4 | Progress tracking | Compare reports against a baseline and show concrete improvements |
| 5 | Documentation and reach | Better examples, translations if needed, and relevant opt-in community sharing |
| 6 | Release and retrospective | Ship a stable release, recognize contributors, and publish the next roadmap |

## Daily operating budget

During the first six follow-up days, maintenance is capped at one hour per day. Issue and pull-request responses take priority over new features. Each session should end with a tested commit and a short record of user-visible changes.

## Measures

Watch meaningful signals together: stars, unique visitors/clones, issue quality, first-response time, successful quick starts, and returning contributors. A star count alone does not show whether the tool works.

## Community guidelines for growth

- Share only in relevant communities where project announcements are allowed.
- Explain a concrete use case instead of asking for empty reciprocal stars.
- Never buy stars, create fake accounts, automate star exchanges, or send unsolicited mass messages.
- Do not open promotional issues on unrelated repositories.
- Credit contributors and label genuinely accessible tasks as `good first issue`.
- Keep all project content professional and free of secrets and sensitive personal data.

## Release checklist

1. Triage new feedback and reproduce reported problems.
2. Run all unit tests on the oldest and newest practical Python versions.
3. Exercise the CLI, reports, scaffolding, and GitHub Action.
4. Update the changelog and version together.
5. Review the full diff for credentials, personal information, and unrelated changes.
6. Tag a signed-off release only after CI passes.
